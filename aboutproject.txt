1. PROJECT OVERVIEW
-------------------

Beginner-friendly overview
RailOpt AI is a railway maintenance decision-support prototype. A client sends operational details for one or more railway assets. The backend applies saved preprocessing and a trained regression model to estimate a maintenance priority score from 0 to 100. For optimization requests, the backend passes eligible assets and the model scores to an OR-Tools CP-SAT scheduler. The scheduler assigns maintenance starts and crews subject to defined track, time-window, crew-capacity, and critical-deadline rules. The result and supporting records are persisted in PostgreSQL and returned as JSON.

The raw workbook is synthetic training data, not a live railway telemetry connection. The system's "asset availability" response is a formula based on planned maintenance hours; it is not a measured reliability or service-uptime prediction.

Technical identity
- Project: RailOpt AI
- Descriptive title: AI-Powered Automatic Block Planning to Maximize Asset Availability for Train Operations
- Problem addressed: prioritizing maintenance and arranging track work in a way that accounts for scarce crews, access windows, track conflicts, traffic peaks, and operational disruption.
- A maintenance block in the project is a time interval in which a maintenance job occupies its track/station conflict group.
- Intended users are described as railway engineers, maintenance planners, section engineers, and block controllers. No user-authentication flow is wired into the currently exposed API.

Actual online workflow
Client-submitted asset records and planning controls
  -> FastAPI/Pydantic validation
  -> shared backend preprocessing and saved model artifacts
  -> XGBoost priority scores
  -> strict priority-threshold selection
  -> OR-Tools CP-SAT schedule
  -> PostgreSQL predictions, asset state, requests, schedules, run, and audit event
  -> JSON response with schedule and aggregate metrics

The optimizer accepts assets in the request body; it does not automatically load a candidate asset set from the database.

3. PROJECT ARCHITECTURE
-----------------------

Actual architecture: modular Python codebase with a client-server/API backend, a separate data/model pipeline, a database, notebooks, and a Streamlit UI shell. It is not a microservice system. It is partly pipeline-based for offline data/training and request-based for online inference/scheduling. It is not a single fully integrated frontend-to-backend application yet.

Component | Purpose | Input -> processing -> output | Main files
Data/model pipeline | Prepare tabular training features and train priority regression | XLSX -> preprocessing/splits -> model artifacts and metrics | src/data/, src/features/, src/models/train.py, notebooks/03_data_preprocessing.ipynb
Model serving | Reuse fitted model transforms and return validated scores | API asset fields -> feature frame -> model predict -> 0..100 scores | backend/app/core/model_registry.py, backend/app/utils/preprocessing.py, backend/app/services/prediction_service.py
API | Validate requests and expose asset, prediction, optimization, and dashboard operations | HTTP JSON -> Pydantic -> service -> JSON | backend/app/main.py, backend/app/api/
Optimization | Choose start offsets and schedule tasks | Eligible assets and model priorities -> CP-SAT -> schedule | backend/app/services/optimization_service.py
Persistence | Store current assets and operation/prediction history | ORM entities and transaction commits -> PostgreSQL | backend/app/database/, backend/migrations/
UI shell | Present prototype navigation and a raw workbook preview | Local XLSX on explicit button -> Streamlit dataframe | frontend/app.py

Important: frontend currently does not call the backend. Its metrics are hard-coded, its prediction and optimization views are text placeholders, and its raw-data preview reads the workbook directly.

7. MACHINE LEARNING
-------------------

Problem type: supervised regression for maintenance priority, not binary classification and not failure probability prediction.

Production training implementation: src/models/train.py.
1. Reads existing train/validation/test CSVs and rejects empty splits, schema mismatches, missing/non-numeric/non-finite values, or target outside 0..100.
2. Loads existing scaler and six fitted categorical encoders and checks that the feature schema matches backend contract.
3. Compares two candidates: XGBoost tree booster and XGBoost linear booster.
4. Selects highest validation R2, with lower validation RMSE tie-break.
5. Refits selected model on train plus validation; keeps test for final evaluation.
6. Saves best_model.pkl, feature_columns.pkl, and training_metrics.json. Reuses scaler/encoders unchanged.
7. BoundedPriorityRegressor clips estimator output to [0,100]; backend validates finite values and score range.

Saved result (outputs/reports/training_metrics.json):
- Selected model: "Gradient-Boosted Trees" XGBRegressor.
- Validation: MAE 0.3646, RMSE 0.5987, R2 0.9976.
- Final train+validation refit fit metrics: MAE 0.1504, RMSE 0.2080, R2 0.9997.
- Held-out test: MAE 0.3179, RMSE 0.5102, R2 0.9982.
- Training split rows: 4,900; validation: 1,050; test: 1,050.
- Comparator, Regularized Linear Booster validation: MAE 2.2625, RMSE 3.6781, R2 0.9094.

Artifacts present: outputs/models/best_model.pkl; feature_columns.pkl; scaler.pkl; encoders/encoder_{asset_type,zone,weather,defect_severity,passenger_peak,nearby_alternate_track}.joblib. Registry loading and backend inference on real workbook rows were run successfully; score values were finite and in range. This does not validate generalization to real operational data.

Not implemented: failure classifier/training labels; calibrated failure probability model; production retraining trigger/monitoring; automated drift assessment. src/models/predict.py is placeholder; serving inference uses backend/app/services/prediction_service.py.


8. OPTIMIZATION / BLOCK SCHEDULING
----------------------------------

Active optimizer: OR-Tools CP-SAT in backend/app/services/optimization_service.py. The separate src/models/optimize.py is a stub, and the optimization notebook is unexecuted.

Decision variables per priority-eligible asset include Boolean scheduled flag, integer start/end hour offsets, peak-overlap hours, daytime-window indicator, and an optional interval. Unscheduled assets use a sentinel start offset.

Input: request assets and crew/horizon/threshold controls; predicted priority from the shared ML service. Priority threshold comparison is strict: priority > priority_threshold (default 75). Critical if priority >= critical_priority_threshold (default 95). Threshold ordering is schema-validated.

Hard constraints:
- Task interval duration is max(1, ceil(maintenance_duration)).
- Start/end must fit the planning horizon and one of the generated allowed windows.
- Standard tasks use overnight 20:00-08:00 windows; critical tasks may also use 00:00-12:00 daytime window.
- Critical assets must be scheduled, with start offset strictly less than 24 hours. If other hard constraints make this impossible, the model may be infeasible and API returns an error.
- Same track groups cannot overlap, using track_id or fallback station as group, through AddNoOverlap.
- AddCumulative caps simultaneous one-crew tasks at request.available_crews.
- Asset crew_available == 0 forces its task unscheduled.

Soft/objective factors:
- Rewards scheduling and higher priority, earlier completion, and using available crew-hours.
- Penalizes estimated train impact, maintenance duration, missing alternate track, passenger-peak overlaps, and critical daytime use.
- Passenger peaks are 07:00-10:00 and 16:00-20:00. Passenger peak asset flag doubles the overlap penalty. Peak is a penalty, not an absolute exclusion.
- Alternate track absence is an objective penalty, not a hard constraint.
- Objective weights live in backend/app/core/constants.py. The solver uses configured seconds (default 30), one worker, and fixed random seed 42. Solver can report OPTIMAL or FEASIBLE.
- Crew names are assigned after solving by placing sorted scheduled jobs on earliest-free crews; each scheduled task consumes one crew.

Schedule output includes asset/track/station, start/end, crew, ML score, schedule status, duration, and objective-derived per-item score. Response metrics include schedule count/request count, delay, availability, crew utilization, completion, estimated impacts, objective value, status, and solver time.

Metric definitions are important:
- availability = 100 * (1 - scheduled maintenance hours / (input asset count * horizon hours)).
- crew utilization = 100 * (scheduled maintenance hours / (available crews * horizon hours)).
- completion = scheduled eligible tasks / eligible request count * 100.
- estimated train impacts per job = ceil(train_frequency * rounded_duration / 24).
These are model/service formulas, not measured fleet availability or actual delayed trains. Scheduling is decision support, not dispatch authority.

16. AI/ML + OPTIMIZATION RELATIONSHIP
------------------------------------

The ML component estimates a continuous maintenance priority score. It does not forecast failure probability as its target. The API caller supplies predicted_failure_probability among asset inputs; model uses that value as one of its features.

The optimizer receives each asset and its score, decides whether/when to schedule eligible work, and assigns crew labels. ML supplies a ranking signal but cannot by itself coordinate shared crew/time/track resources. CP-SAT can enforce combinatorial scheduling constraints but does not infer risk priority from sensor/asset predictors. Together, they provide prioritization followed by constrained scheduling.

The integration is active in the FastAPI path; the older standalone src/models/predict.py and src/models/optimize.py are not active implementations.

27. PROJECT EXPLANATION FOR VIVA
-------------------------------

30-second explanation:
RailOpt AI is a railway maintenance decision-support prototype. It takes asset condition and operating information, uses a trained XGBoost regression model to estimate maintenance priority, and passes those scores to an OR-Tools CP-SAT scheduler. The scheduler creates maintenance block times while respecting crew, track conflict, allowed window, and critical deadline constraints. A FastAPI backend persists the results in PostgreSQL. The training workbook is synthetic and the Streamlit dashboard is still a prototype shell.

1-minute explanation:
The offline pipeline uses a 7,000-row synthetic railway dataset, feature transformations, and train/validation/test splits. The trained XGBoost model predicts a priority_score from 24 numeric features; it does not predict failure probability. At runtime, FastAPI validates the incoming asset data, loads the saved model and preprocessing artifacts, and scores each asset. CP-SAT then schedules those above the configured threshold under time-window, same-track, crew-capacity, and critical-asset rules. PostgreSQL stores asset state, prediction history, run, maintenance requests, schedule rows, and audit events. The API and DB health have been verified; UI integration and real-data validation remain future work.

3-minute explanation:
Railway maintenance planning must balance asset condition, limited maintenance crews, safe work windows, shared tracks, train disruption, and urgent jobs. RailOpt AI separates prediction from planning. The data stage starts with a synthetic Excel dataset. Existing preprocessing outputs create 70/15/15 train/validation/test CSVs, encode categorical columns, scale numerical columns, and add five derived signals. The training script compares two XGBoost regressors and selects the one with best validation R2, using RMSE as a tie-breaker. The saved model is wrapped to keep the score in 0-100; the backend loads the model, saved feature order, scaler, and six encoders at startup.

An optimization request supplies assets and planning settings. The prediction service prepares the 24-feature frame and computes priority. Priority above the threshold is eligible; critical scores must meet their higher threshold. The CP-SAT model enumerates permitted maintenance windows, creates optional intervals, prevents overlapping work in a shared track/station group, and caps concurrent work by crews. It rewards scheduled/high-priority/early work and penalizes estimated train impact, duration, peak overlap, lack of alternate track, and critical daytime scheduling. The response returns schedule items and formula-based metrics, and the backend persists operational records in PostgreSQL.

The database schema is managed through Alembic. The current local migration is 0001_initial_schema. FastAPI root/health and model/database startup have been verified. The schedule service was exercised previously with actual model/data against isolated SQLite, but optimization writes through the currently migrated PostgreSQL database still need a dedicated end-to-end test. The current Streamlit page has static metrics and placeholder prediction/optimization pages and is not connected to the backend.

What technologies did you use?
Python, FastAPI/Uvicorn, Pydantic, SQLAlchemy, PostgreSQL/Alembic, Pandas/NumPy, scikit-learn preprocessing, XGBoost regression, OR-Tools CP-SAT, Joblib, Jupyter, Matplotlib/Seaborn, and a partial Streamlit UI.

Why Python?
The project uses Python for its data processing, model training/inference, API, ORM access, and optimization integrations in one language. This answer describes the observed implementation, not a comparison benchmark.

Why XGBoost?
The training code compares a tree-based XGBRegressor with an XGBoost linear booster. The tree model had better validation R2/RMSE on the supplied synthetic splits and was saved. It was not proven superior on real railway data.

Why optimization?
An ML score ranks urgency but cannot coordinate shared time intervals, track conflicts, maintenance windows, crews, and critical deadlines. CP-SAT handles those discrete scheduling decisions and constraints.

What is block planning?
In this implementation it is assigning a maintenance task a start/end interval in a track/station group, with crew and time-window rules; the workbook itself does not contain a railway timetable or measured possession feed.

How does the system maximize asset availability?
The objective rewards scheduled work and prioritizes high scores/earlier completion while penalizing several disruption costs. The reported availability percentage is a scheduled-hours formula, not proof of increased real-world uptime.

What is the input?
Asset identity/type/zone/station and optional track ID, age, inspection/defect/maintenance history, traffic/speed/axle load, environment, crew, duration, alternate-track/passenger-peak flags, supplied failure-probability value, and planning controls.

What is the output?
Predicted priority, scheduled/not-scheduled disposition, start/end, crew label, solver/run metrics, and database records.

What is the novelty?
The implemented integration combines a trained priority regressor with CP-SAT block scheduling in a persisted FastAPI workflow. Novelty or research contribution has not been independently established by the repository.

What are the limitations?
Synthetic data, supplied rather than predicted failure probability, simplified operational inputs/availability metrics, unconnected UI, missing auth and automated tests, and no demonstrated real-world safety/operations validation.

What would you improve?
First test the API and persistence end-to-end against PostgreSQL; connect the UI to real API results; then evaluate with real labelled asset histories and railway-approved operational constraints.
